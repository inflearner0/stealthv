# stealthv

**A minimal AMD-V (SVM) hypervisor for Windows x64, with nested-paging code
hooks that are invisible to anything reading memory.**

*stealth + `hv`.* Read a hooked page and you get the original instructions;
execute it and you get a substitution. Time a `CPUID` and it costs exactly what
the bare processor costs, because it never left it.
Read the driver's own pages and they are zeroes. Not being seen is not a feature
here, it is the design — the same trick applied in four places.

A **blue pill** / **hyperjacking** research tool: a kernel driver that puts the
**already running** Windows kernel into an SVM guest, installs **EPT-style
hypervisor hooks** through **nested page tables (NPT)**, and studies **hypervisor
detection** from inside the guest. The AMD counterpart to the Intel VT-x/EPT
projects.

> **A lab instrument.** This is a type-2 hypervisor that hides itself from the
> guest, installs invisible kernel hooks, and runs caller-supplied shellcode in
> kernel mode on request. It exists to study how a driver behaves under
> virtualisation and how much of a hypervisor a guest can detect. Run it on
> machines you own, on an isolated network, and read the *What is and is not
> tested* section before trusting it with anything.

Every logical processor captures its own state, executes `VMRUN`, and carries on
running the exact instruction it was about to run — one privilege level further
down. The guest runs under nested page tables that map every guest physical page
to itself: the point of an identity map is not isolation but control over
permissions, and a page that is non-executable in one hierarchy and
executable-but-substituted in another is enough to hold a code hook nothing can
find by reading memory.

| Intercept | Why |
|---|---|
| `RDMSR`/`WRMSR` of `EFER` | keep `EFER.SVME` set and hide it from the guest |
| `VMMCALL` | the control channel and the unload doorbell, on the magic in RAX; forwarded to the hypervisor above us otherwise |
| `VMRUN`, `VMLOAD`, `VMSAVE`, `STGI`, `CLGI`, `SKINIT`, `INVLPGA` | inject `#UD` — what a CPU with `EFER.SVME` clear does |
| `#NPF` | the hook engine: the guest crossed between code and data on a hooked page |

## Build

```powershell
.\build.ps1 -Sign
```

Produces `bin\svmhv.sys` (test-signed), `bin\svmhvctl.exe`, `bin\hvtest.exe`
and `bin\svmhv-test.cer`.

Needs Visual Studio with the C++ toolset and the WDK. Both are discovered:
`vswhere` finds the toolset, and the newest Windows Kit that actually ships
`km\` headers is used as the WDK. Override with `-VsPath`, `-KitRoot` or
`-SdkVersion` if you have several installed.

Prebuilt, test-signed binaries are attached to each [release](../../releases).
The certificate in the archive is generated by that build and is not a trust
anchor — it exists so Windows will load the driver with testsigning on, nothing
more.

## Run

The target needs `bcdedit /set testsigning on`, the test certificate in `Root`
and `TrustedPublisher`, and — importantly — **no other hypervisor owning SVM**
(`bcdedit /set hypervisorlaunchtype off`, VBS/HVCI disabled).

```powershell
sc.exe create svmhv type= kernel binPath= C:\lab\svmhv.sys
sc.exe start svmhv
.\hvtest.exe
sc.exe stop svmhv
```

## Driving it: there is no IOCTL

The driver has **no device object, no symbolic link and no dispatch routines**.
Nothing it does is reachable from user mode. Its entire interface is one exported
structure, `svmhv!g_Control`, and a worker thread that polls it every 100 ms: a
client writes a command and waits for `Completed` to catch up with `Sequence`.

That split is deliberate, and it is most of why this is small. Only the
operations that have to **run kernel code** go through the doorbell — installing
a hook allocates a shadow page, pins the target with an MDL, builds a trampoline,
splits the nested page tables and IPIs every processor. Reading a counter does
not, so the worker republishes every counter, the hook table and the last
self-test into `g_Snapshot`, and a client just reads it. A kernel debugger can do
all of that with `eq` and `dq`.

Two clients ship with it. `svmhvctl.exe` is a ring-3 tool that talks over the
`VMMCALL` channel directly. `mcp/svmhv_agent.py` is an MCP server that runs
**inside the guest** and drives `svmhvctl` over HTTP, so an assistant on another
machine can install hooks and read traces without a debugger attached. See
`mcp/README.md`.

## Hooks, traces and watchpoints

Three things trap, all through one mechanism: a page whose entry in the primary
hierarchy is missing a permission, and whose entry in the shadow hierarchy has it.

| kind | primary view | shadow view | traps |
|---|---|---|---|
| exec | original page, not executable | patched copy, executable | instruction fetch |
| write watch | original page, not writable | original page, writable | stores |
| access watch | not present | present, writable, executable | everything, reads included |

Every one resolves the same way: record it, switch this processor to the shadow
hierarchy, re-execute. The instruction completes, and because nothing else is
executable there, the next fetch outside the page faults straight back. No
single-stepping, no trap flag, and no need to decode the faulting instruction.

A hook can also be narrowed and armed:

- **only for a process** - matched against the image name in EPROCESS, so
  `notepad.exe` works without chasing PIDs that change every launch.
- **only when a particular driver calls it** - a filter on the *return address*
  against a module's range, which is what says whose code we are standing in.
- **dereference a pointer argument** - ANSI, wide, `UNICODE_STRING*` or
  `OBJECT_ATTRIBUTES*` (which walks to its `ObjectName`, what nearly every
  `Nt*` path argument really is). Only taken at IRQL <= APC_LEVEL, only for
  addresses the memory manager admits to, and under SEH; a capture that cannot
  be taken safely comes back empty.
- **replace arguments on the way through** - the recorder holds the register
  frame the thunk is about to restore, so writing it is all it takes.
- **refuse the call** - the continuation becomes a `mov rax, imm64; ret` stub,
  which returns through the caller's own return address without the original
  ever running.

An exec hook's action is one of three things:

- **trace** — the driver generates a 24-byte stub per hook that loads the hook id
  into R11 (volatile, and not an argument register) and jumps to `AsmTraceEntry`,
  which preserves every volatile register including XMM0–5, records the call, and
  continues into the trampoline. Captures RCX/RDX/R8/R9, four stack arguments,
  the return address, RSP, processor, PID/TID and IRQL. Cheap per-hook filters
  let a function called ten thousand times a second be traced for only the calls
  that matter.
- **detour** — jump to a kernel address the caller already has.
- **shellcode** — jump to caller-supplied bytes, entered with the target's
  arguments intact. `ret` replaces the function; falling off the end continues
  into it.

The trampoline holds the original prologue followed by a jump past it, so a
detour can always call through to the real thing.

### Watchpoints will starve the guest if you point them at the wrong page

A write watch fires **twice per store** — once to reach the permissive view, once
to leave it. On a page written in bulk that is thousands of exits a second. A
watch put on the driver's own snapshot page during development produced 53 000
events in eight seconds and starved the guest badly enough to cost the VM.

Two guards exist because of that, and neither makes it a good idea:

- the driver refuses a watch on its own control block, snapshot or trace ring
  (`STATUS_ACCESS_DENIED`, verified);
- the worker disarms any watch producing more than 20000 hits in one 100 ms
  interval and logs it.

Watch data you expect to be touched rarely. For anything frequent, use an exec
hook with a filter.

## Configuration

There is no registry key, and nothing is read at load time. Every option is a
constant in `driver/config.h`, folded into the code at build time.

That is itself a concealment decision. A driver that reads its own settings out
of `HKLM` leaves the settings sitting in `HKLM`, where anyone curious about the
machine can read the exact list of what is being hidden from them and switch it
off — and the read is a behaviour worth noticing in its own right. The only way
to change any of this is to rebuild.

| Constant | Default | What it does |
|---|---|---|
| `STEALTHV_NESTED_PAGING` | 1 | nested page tables, and therefore hooks and page hiding |
| `STEALTHV_HIDE_SVM_CPUID` | 0 | impossible without intercepting `CPUID`; see above |
| `STEALTHV_HIDE_EFER` | 1 | intercept `EFER` so `SVME` reads as clear |
| `STEALTHV_TSC_OFFSET` | 0 | removed: `CPUID` is not intercepted, so there is no cost |
| `STEALTHV_HIDE_PAGES` | 1 | the driver's own pages read as zeroes |
| `STEALTHV_ALWAYS_FLUSH_TLB` | 0 | flush the ASID every entry — **leave this off** |
| `STEALTHV_CONTROL_INTERFACE` | 1 | answer the control leaf and run its worker |

Everything defaults to the most concealed setting it can. Two are worth knowing
about before you change them: `STEALTHV_HIDE_EFER` costs about 200 000 exits per
second under a parent hypervisor (Hyper-V's synthetic MSRs sit outside every
MSRPM range), and `STEALTHV_CONTROL_INTERFACE 0` removes the interface entirely
— nothing to open, no worker thread — at the cost of `svmhvctl` and the MCP
server. The reasoning for both is in [CLAUDE.md](CLAUDE.md).

A processor without nested paging, or a host with `EFER.NXE` clear, now **refuses
to load** rather than quietly running with the hooks and page hiding absent.

## What is and is not tested

Verified in the lab VM (Ryzen 9 6900HS, 8 vCPU, Windows 11 22621, nested under
Hyper-V), twice per run with zero failures:

```
[pass] the channel is silent without the magic
[pass] cpuid is not intercepted: no exit, nothing to time   (cpuid exits: 0)
[pass] nested paging is on
[pass] hook installed
[pass] the detour ran
[pass] the trampoline reached the original code
[pass] reading the hooked function returns the original bytes
[pass] every processor saw the hook, concurrently        (8 ok, 0 missed)
[pass] unhook restored it
```

plus a clean unload that restores the guest's view of SVM exactly, and the
hypervisor's own pages reading as zeroes from inside the guest. `CPUID` measures
2376 cycles against a 2376-cycle native baseline.

**The guest used to reset a few minutes after load. That is fixed.** It was
described for a long time as a hang, and it was not — it was a hard reset, and
`Uptime`, `Heartbeat` and PowerShell Direct all disguised it. The cause was the
TSC compensation that intercepting `CPUID` made necessary; not intercepting it
removed both. Verified with every option enabled: 200 s and 220 s with an
unchanged boot time, service RUNNING, `hvtest` at `RESULT: OK`, and
`cpuid_exits=0` across 461 123 exits.

**Long-duration stability under concurrent load is still not verified.**
`soak.ps1` has not been re-run since the fix. Minutes of idle stability is not
hours of load. If you are chasing a stability problem here, read the ground
rules in [CLAUDE.md](CLAUDE.md) first — most of the obvious instruments lie.

## Limitations

Deliberate, in the name of staying readable:

- The nested page tables are an identity map. This can filter and observe, and
  it can hide a hook; it cannot isolate memory from the guest.
- No nesting: a guest `VMRUN` gets `#UD`, and SVM is hidden so it should not try.
- One hook per guest physical page, and the caller supplies the prologue length.
- Remote TLB shootdown has a residual window. A *remote* enlightened flush only
  takes effect on the target processor's next exit. In practice every vCPU exits
  constantly, so the window is short; closing it properly would mean IPI-ing the
  other processors out of guest mode on every flush hypercall.
- The SVM feature bits are visible to the guest. Masking them requires
  intercepting `CPUID`, which is what produced a timing signature and, through
  the compensation it needed, the resets. This is the deliberate trade; a guest
  that tries to *use* SVM still finds a `#UD` from `VMRUN` where it did not
  expect one.
- Hiding `EFER.SVME` costs about 200 000 extra exits per second under a parent
  hypervisor, and that cost is now paid by default — see *Configuration* above.
  Set `STEALTHV_HIDE_EFER` to 0 to get the throughput back, at the price of a
  ring-0 `RDMSR` seeing `SVME` set.
- `RDMSR`/`WRMSR` exits are not TSC-compensated, and while `EFER` is hidden, an
  MSR the hardware does not implement is passed through inside `__try`/`__except`
  — a `#GP` dispatched with `GIF` clear on the host stack. It should survive
  (the host IDT and GS base are the real ones by then) but it is untested,
  because nothing in the lab guest reads a non-existent MSR.
- No support for CPUs without NRIP-save beyond the fixed instruction lengths of
  the instructions actually intercepted.
- The exit handler bugchecks on any exit it does not recognise, on purpose: a
  silent wrong answer in a hypervisor is worse than a crash dump.
- XMM6–15 are left to the C ABI; only XMM0–5 are saved around the handler.
## Layout

```
driver/     the kernel driver
  svm.h         VMCB layout and SVM constants, every offset C_ASSERTed
  svmhv.c/.h    capability checks, VMCB setup, the #VMEXIT handler, concealment
  npt.c/.h      the two identity-mapping hierarchies, splitting, page hiding
  hook.c/.h     shadow-page hooks and watchpoints
  trace.c/.h    the trace ring and the argument recorder
  control.c/.h  the doorbell and the worker thread that answers it
  hvcall.c/.h   the VMMCALL control channel
  svmasm.asm    the VMRUN loop, the devirtualise tail, the trace thunk
include/    svmhvctl.h - the control interface, shared with the tools
tools/      svmhvctl.c + hvasm.asm (the VMMCALL client), hvtest.c (the probe)
mcp/        svmhv_agent.py - the in-guest MCP server, and its README
scripts/    runtests.ps1, soak.ps1 - in-guest test runs
bin/        build output, not in source control
```

## Continuous integration

`ci.yml` runs on every push and pull request: it installs the WDK, builds the
driver and both tools with `/WX`, and runs `mcp/test_agent.py`.

No hosted runner has an AMD processor with SVM, so **CI never executes the
hypervisor**. What it does catch is a warning, and the `C_ASSERT`s in
`include/svmhvctl.h` that fail the build if a structure the driver and its
clients share ever drifts apart — that one already caught the trace record
growing from 152 to 432 bytes. Anything needing the hypervisor actually running
has to be run by hand in a VM; see `scriptsuntests.ps1`.
